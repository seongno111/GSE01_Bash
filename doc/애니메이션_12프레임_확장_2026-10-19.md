# 애니메이션 12프레임 확장

작성일: 2026-10-19

## 변경 결과

플레이어, NPC 5직군, 몬스터 2종, 보스, 변이 캐릭터의 보행을 각각 6프레임에서 12프레임으로 늘렸다. 변이 잔영과 적 거점 몬스터도 같은 보행 클립을 사용한다. 플레이어 공격은 인간·변이 상태 각각 12프레임으로 늘렸다.

총 애니메이션 이미지는 보행 120장, 공격 24장으로 144장이다. 기존 72개 포즈를 보존하고 실제 중간 포즈 72개를 새 PNG에 추가했다. 기존 프레임을 복제하거나 불투명도만 섞는 방식이 아니다.

각 클립은 `기존0 → 중간0 → 기존1 → 중간1 → … → 기존5 → 중간5`로 재생한다. 보행의 마지막 중간 포즈는 첫 포즈로 이어지는 동작이고, 공격의 마지막 중간 포즈는 공격 시작으로 되돌아가지 않는 복귀 자세이다.

기존 보행 거리 2.2당 한 주기, 공격 길이 0.22~0.32초, 발사체 생성 시점과 쿨타임을 유지했다. 기존 포즈가 등장하는 주기 내 시점도 유지되며 그 사이에 새 포즈가 들어간다. 좌우 반전과 공격 방향 고정 방식은 동일하다.

## 생성 에셋과 재생 구조

| 새 파일 | 배열 | 중간 포즈 수 |
| --- | --- | --- |
| `SimpleGame/Assets/unit-walk-humans-inbetweens-v2.png` | 6열 × 6행 | 36 |
| `SimpleGame/Assets/unit-walk-monsters-inbetweens-v2.png` | 6열 × 4행 | 24 |
| `SimpleGame/Assets/player-attack-inbetweens-v2.png` | 6열 × 2행 | 12 |

각 PNG의 같은 이름 `.prompts.json`에 생성 프롬프트와 참조 파일을 저장했다. 내장 `image_gen`을 사용했고, 기존 v1 보행·공격 시트를 외형과 동작의 참조로 사용했다. 기존 PNG는 그대로 유지한다. Python은 이미지의 alpha/좌표 분석과 검사 JSON 작성에만 사용했다.

`Renderer::SpriteClip`의 고정 길이 배열을 가변 프레임 목록으로 바꿨다. 재생 인덱스는 실제 `frames.size()`를 기준으로 계산하므로 향후 다른 프레임 수의 클립을 연결할 수 있다. 현 시트 로딩 규격은 기존 6개 키 포즈와 새 6개 중간 포즈의 교대 구성이다.

각 원본 시트의 행마다 공통 중앙값 높이를 기준으로 크기를 맞추고, 일정한 셀 중심과 발 아래쪽을 피벗으로 사용한다. 이 때문에 원본 해상도나 여백이 달라도 클립 전환으로 크기가 크게 달라지지 않는다. 다리마다 움직이는 발의 중심을 피벗으로 삼지 않으므로 보폭에 따라 몸 전체가 좌우로 이동하는 것을 피한다. 생성 에셋의 의상·손 위치 등 미세한 연속성은 실제 플레이 화면에서 최종 확인이 필요하다.

추가 시트가 누락되거나 해당 행의 일부 프레임이 비어 있으면 그 클립 전체를 기존 6프레임으로 대체한다. 빠진 중간 프레임만 기존 포즈로 반복해 리듬이 불규칙해지는 처리를 하지 않는다.

## 텍스처와 성능

종전에는 PNG 4장 전체를 GPU atlas에 배치했다. 이번에는 PNG 7장에서 실제 그림이 있는 사각형만 추출해 높이 순서로 정렬하고, 행 단위로 빈 공간을 채워 하나의 atlas에 배치한다. 각 영역의 주위에는 2픽셀 투명 여백을 두고 UV를 반 texel 안쪽으로 제한한다.

이 처리는 게임 시작 시 한 번 수행한다. 디스크의 PNG를 다시 저장하거나 프레임마다 이미지를 디코딩·변형하지 않는다. 인스턴스의 UV만 바꾸며 공유 사각형 메시, 순서 보존 인스턴싱, 인스턴스당 80바이트 데이터, 단일 GPU 텍스처를 유지한다. 프레임 수 증가 때문에 유닛당 드로우콜이나 삼각형 수가 늘지 않는다.

정적 분석 기준 정상 리소스의 예상 배치는 다음과 같다. 실제 실행 측정값은 아니다.

| 항목 | 이전 | 확장 후 |
| --- | ---: | ---: |
| 보행 클립당 프레임 | 6 | 12 |
| 플레이어 공격 클립당 프레임 | 6 | 12 |
| 총 애니메이션 프레임 | 72 | 144 |
| 환경 등 정적 셀 | 16 | 16 |
| GPU atlas 크기 | 3714 × 2284 | 2423 × 2484 |
| RGBA8 상주 바이트 | 33,931,104 | 24,074,928 |
| GPU atlas 메모리 | 약 32.36MiB | 약 22.96MiB |

보관하는 포즈는 2배로 늘었지만 여백을 줄여 GPU atlas 크기는 약 29% 감소했다. 시작 시에는 추가 PNG 3장을 디코딩하고 프레임을 배치하는 비용이 발생한다. 실행 중 FPS 개선이나 시작 시간은 측정하지 않았다.

GPU 텍스처 크기 제한 안에 들어가지 않으면 모든 중간 포즈를 제외하고 기존 6프레임 배치를 재시도한다. 그것도 불가능한 경우 정적 셀만 사용한다. 2048 크기 제한을 가정한 정적 계산에서는 기존 6프레임이 1926 × 1683, 12,965,832바이트로 들어간다. 4096 이상 제한에서는 현재 12프레임 전체가 들어간다.

플레이어 등불의 발광 영역도 새 포즈마다 초기화 시 찾으며, 의복 전체를 발광시키지 않고 Bloom을 유지한다.

## 로그와 검토 기록

시작 로그에서 전체 프레임 수와 클립별 프레임 수를 확인할 수 있다.

```text
[Assets] Packed sprite atlas ... staticCells=16 walkClips=10 attackClips=2 animationFrames=144 ...
[Assets] Unit sprite=0 walkFrames=12 attackFrames=12
[Assets] Unit sprite=1 walkFrames=12 attackFrames=0
...
[Assets] Unit sprite=9 walkFrames=12 attackFrames=12
```

`residentBytes`, `cropBytes`, `textureLimit`을 함께 기록한다. 정상적인 중간 시트가 있는 경우 보행은 0~9번 모두 12프레임, 공격은 0번과 9번만 12프레임이다. 누락 리소스나 GPU 한계로 6프레임 대체가 일어나면 이유도 로그로 출력한다.

`애니메이션_12프레임_에셋검토_2026-10-19.json`에 이미지 경계, 프레임 수, atlas 배치와 한계별 검사 결과를 저장했다. alpha 구분선, 모든 셀의 유효성, 배치 영역의 비중첩·메모리 경계, 6/12프레임 인덱스 끝값을 정적으로 검토했다. 프로젝트 PNG 등록과 복사 설정, 코드 컨벤션도 확인했다.

사용자 요청에 따라 빌드·게임 실행은 하지 않았다. 빌드 후 `Assets`에 새 PNG 3개가 복사되는지, 로그가 144프레임을 표시하는지, 기존 포즈와 새 포즈 사이에서 발·몸 크기·등불이 안정적인지 확인하면 된다. NPC·몬스터 공격 애니메이션은 기존 요청대로 추가하지 않았다.
