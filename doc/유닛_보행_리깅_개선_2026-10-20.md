# 유닛 보행 떨림·다리 교차·상체 움직임 개선

작성일: 2026-10-20

## 문제와 원인

- 기존 12프레임 방식은 별도로 생성한 두 시트를 번갈아 사용했다. 자세뿐 아니라 얼굴·옷·장비의 모양과 외곽선도 달라져 재생할 때 몸이 떨리는 문제가 있었다.
- 보행 이미지에 같은 다리가 계속 앞으로 나오는 자세가 많았다. 프레임 수만 늘려서는 양발이 번갈아 디디는 동작을 보장할 수 없었다.
- 몸통과 어깨가 같은 방향으로 고정되어 다리 움직임과 연결되지 않았다.
- 실제 이동량을 받은 순간에 보행 위상을 바꿔서, 20Hz로 움직이는 NPC는 화면 갱신 사이에 자세가 멈추고 뛰었다. 기존 보폭 2.2 기준 플레이어의 달리기는 초당 약 2.94주기로 빨랐다.

## 적용 방식

전체 캐릭터 이미지를 프레임마다 교체하던 경로를 부위별 스프라이트를 연속 변환하는 2D 리깅으로 교체했다. 고정된 그림의 관절과 위치를 움직이므로 프레임 사이에 옷이나 얼굴의 형태가 바뀌지 않는다. 표현 가능한 자세 수는 기존의 12장에 제한되지 않는다.

적용 대상은 플레이어, 5개 NPC 직군, 일반 몬스터, 무장 몬스터, 보스, 변이 캐릭터의 총 10종이다. 변이 NPC와 죽음의 잔재도 같은 렌더링 경로를 사용한다.

### 보행과 상체

- 각 캐릭터를 가슴·머리, 골반, 양팔, 양쪽 허벅지·종아리의 8개 부위로 구성했다.
- 양쪽 다리를 반 주기 차이로 움직인다. 앞서는 발이 교대로 바뀌고, 앞으로 옮기는 발을 들어 올린다.
- 발의 목표 위치에 맞춰 고관절과 무릎을 푸는 2관절 IK를 적용했다. 허벅지와 종아리는 원본 그림의 길이 비율을 유지해서 무릎 연결부의 크기 차이를 줄였다.
- 앞발 쪽 골반과 반대 방향으로 가슴을 회전시킨다. 어깨의 전후 위치와 높이도 반대로 바꾸고, 팔은 같은 쪽 다리와 반대로 흔든다.
- 몸통의 가벼운 기울기와 가로 변형으로 체중 이동을 표현한다. 캐릭터 전체에 상하 이동을 더하는 방식은 사용하지 않는다.
- 몸통과 어깨의 연결 위치를 함께 계산하고, 허리와 무릎 그림을 일부 겹쳐 관절 틈을 줄였다.
- 좌우 방향 전환은 전체 관절 좌표를 같은 기준점으로 반전한다. 정면·후면 전용 그림은 이번 범위에 포함하지 않는다.

### 재생 속도와 전환

- 실제 충돌 처리 후 이동량을 0.10초 구간으로 모아 속도를 계산하고, 화면 갱신마다 보행 위상을 연속적으로 진행한다.
- `SceneGraph::UpdateVisuals`가 플레이어·적·NPC의 이동 처리 이후 한 번 호출된다. 화면 밖 유닛도 같은 방식으로 위상을 진행하며 지형·소품은 이 순회에서 제외된다.
- 보폭을 3.6으로 설정했다. 플레이어 일반 이동 속도 3.7에서 약 1.03주기/초, 달리기 6.475에서 약 1.80주기/초다. 상한은 1.8주기/초다. 한 주기는 양발의 두 걸음이다.
- 시작·정지 시 동작의 크기를 완만하게 변경하고, 정지할 때 보행 위상을 0으로 즉시 되돌리지 않는다.
- NPC의 경로 노드 전환 중 짧은 공백을 흡수한다. 수직에 가까운 이동에서 작은 가로 방향 변화 때문에 좌우가 뒤집히는 현상도 줄였다.

### 플레이어 공격

몸통과 팔에 부드러운 공격 동작을 더한다. 공격 시작과 종료에서 변위와 변화율이 0이 되는 곡선을 사용해 보행으로 돌아올 때 자세가 갑자기 교체되지 않는다. 이동 중에도 다리의 보행 주기는 이어진다. 기존 발사체 생성 시점, 피해량, 공격 쿨타임은 변경하지 않았다. NPC·몬스터의 신규 공격 동작은 추가하지 않았다.

## 리소스와 렌더링

새 리소스는 `SimpleGame/Assets/unit-rigs-humans-v3.png`와 `unit-rigs-monsters-v3.png`다. 각각 5열×6행, 5열×4행이며 열 순서는 몸통, 먼 팔, 먼 다리, 가까운 다리, 가까운 팔이다. 생성 및 수정 프롬프트는 같은 이름의 `.prompts.json`에 저장했다.

`RendererSprites.cpp`가 시작 시 투명한 행·열 경계와 각 부위의 범위를 읽고, 몸통과 다리를 관절 기준으로 나눠 한 텍스처에 배치한다. `RendererRig.cpp`는 해당 부위의 변환값만 기존 인스턴스 버퍼에 제출한다. 프레임마다 PNG 읽기, 텍스처 업로드, 부위 메시 생성은 하지 않는다.

| 항목 | 이전 12프레임 경로 | 이번 연속 리깅 경로 |
|---|---:|---:|
| 유닛 1개당 스프라이트 인스턴스 | 1 | 8 |
| 유닛 1개당 스프라이트 삼각형 | 2 | 16 |
| 유닛 1개당 변환 인스턴스 데이터 | 80바이트 | 640바이트 |
| 텍스처 수 | 1 | 1 |
| 그림 데이터 업로드 | 시작 시 | 시작 시 |
| 원본 기준 패킹 결과 | 24,074,928바이트 | 7,964,992바이트 |

이번 패킹 계산은 최대 텍스처 변 8192를 가정했을 때 773×2576이다. 실제 시작 시에는 GPU의 지원 한도에 맞춰 다시 계산한다. 이전 수치는 2026-10-19 분석 자료 기준이다. 실제 GPU 메모리 할당량과 FPS를 측정한 수치는 아니다.

8개 부위는 같은 텍스처·공유 사각형 메시·기존 순서 보존 배치에 들어간다. 부위마다 별도의 `glDraw`를 호출하지 않는다. 다만 인스턴스와 삼각형 수는 늘어나므로 버퍼 용량 한도에 도달하면 추가 배치가 발생할 수 있다. 기존 프로파일러의 Instances, Triangles, InstanceBytes, CapacityFlushes, GPU 시간으로 비용을 비교할 수 있다.

플레이어 등불은 가까운 팔의 밝은 유리 영역만 발광 마스크로 지정해 기존 HDR/Bloom 경로를 유지한다. 마스크도 팔과 함께 이동·회전·반전된다.

기존 v1/v2 이미지 파일은 이력으로 남겼지만 현재 로더는 교차 재생용 시트를 읽지 않는다. 리깅 이미지가 누락되거나 유효하지 않으면 콘솔에 이유를 남기고 정적 스프라이트로 대체한다.

## 분석 로그와 정적 확인

시작 로그에 텍스처 크기, 정적 영역 수, 리그 수, 부위 수, 등불 마스크 수, 이미지 바이트 수를 기록한다. 각 유닛에는 `mode=continuous-rig`, `parts=8`, 보폭과 재생 상한을 기록한다. 리소스가 정상적으로 읽혔을 때의 기대값은 `unitRigs=10`, `rigParts=80`, `lanternParts=1`이다.

정적 검토 상세 결과는 `유닛_보행_리깅_정적검토_2026-10-20.json`에 저장했다.

- 두 새 시트의 투명 경계와 50개 원본 부위가 존재함을 확인했다.
- 80개 리깅 영역과 16개 정적 영역의 패킹 범위 및 겹침을 검사했다.
- 등불 마스크에서 밝은 유리 픽셀 143개를 검출했다.
- 1,441개 위상과 21단계 이동 가중치에서 양다리 목표 위치의 도달 거리를 계산했다. 최대 0.4743H로 설정된 관절 도달 한계 0.484H 안에 있다.
- 프로젝트와 필터 파일에서 새 소스와 PNG가 각각 한 번 등록됨을 확인했다. 기존 빌드 후 PNG 복사 규칙이 새 리소스에도 적용된다.
- 포맷과 변경 파일의 공백 오류를 점검했다.

사용자 요청에 따라 빌드와 게임 실행, 실제 렌더링 결과 확인은 하지 않았다. 부위 연결부의 실제 인상, 발의 접지 표현, 달리기 및 이동 중 연속 공격의 자연스러움은 실행 화면에서 확인할 항목이다. 이 자료의 정적 검사는 컴파일 성공이나 시각 품질 확인을 의미하지 않는다.
