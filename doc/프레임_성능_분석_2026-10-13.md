# 프레임 성능 분석과 개선

분석일: 2026-10-13. 빌드·게임 실행·렌더링 결과 확인은 사용자 요청에 따라 하지 않았다. 아래 측정치는 이미 저장된 이전 실행 로그이며, 변경 후의 성능을 측정한 값이 아니다.

## 기존 로그에서 확인한 원인

분석 대상은 `x64/Release/Profiling/20261013-133906-292-18396/frames-1.csv` 및 같은 폴더의 `session.log`다. 실행 파일 빌드 시각은 2026-10-12 18:57:35, GPU는 AMD Radeon 860M, 해상도는 1280×800, Release 구성이다. 전체 4,363프레임, 약 82.9초 기록이다. 아래 표는 초기 로딩 구간을 구분하기 위해 elapsed_s > 6인 프레임만 사용했다.

각 항목의 최대치는 서로 다른 프레임일 수 있다. CPU 제출 시간은 GPU 처리 시간과 다르다. 이 로그에는 GPU 타이머가 없어 GPU나 후처리가 병목이라고 단정할 수 없다.

프레임 3432는 렌더 CPU 113.098ms 중 캐시 읽기 약 107.926ms가 관측되었다. 프레임 4052는 렌더 CPU 76.824ms, 캐시 쓰기 67.480ms, 새 메시 59개였다. 첫 프레임은 메시 생성 1,551개·디스크 로드 370개, 렌더 CPU 약 4,974.5ms였다. 도형 생성 연산보다 렌더 스레드의 동기 파일 접근이 큰 정지를 만들었다.

## 1. 매 프레임 도형을 새로 만드는가

기존 Renderer에도 메모리/디스크 메시 캐시와 `glDrawArraysInstanced`가 있다. 초기 로딩 이후 모든 도형의 정점을 매 프레임 새로 생성하는 구조는 아니다. 캐시된 정점은 GPU의 RGBA32F 지오메트리 아틀라스에 저장되고, 위치·축·색상·발광 세기는 별도 인스턴스 데이터로 전달한다.

다만 지형 키가 `terrain/<32비트 tile.variant>/<flags>`여서 사실상 타일마다 다른 메시가 생겼다. 이동하면서 새 파일을 생성하거나 읽고, 4,096개 캐시 한도를 넘으면 대량 퇴출과 아틀라스 재업로드도 발생했다. 파일에 저장한다고 공유와 재사용이 충분해지는 것은 아니었다.

변경 후 지형은 공통 바닥 1개와 장식 64개를 사용한다. 지형색·밝기는 인스턴스 tint로 전달하고, 길·오염 흔적·격자 선은 기존 공통 기본 도형을 사용한다. 새 지형 키는 최대 65개이며 좌표나 전체 난수값에 따라 무한히 늘어나지 않는다. 바닥 색상 변화와 오염 표현은 유지하고 장식 선 배치는 결정적인 64개 패턴으로 재편했다. 장식 패턴의 반복은 이번 변경의 시각적 차이다.

같은 메시를 여러 위치에 제출하더라도 실제 GL 호출은 배치로 합쳐진다. 현재 방식은 물체 단위가 아닌 **삼각형 단위 인스턴싱**으로, 서로 다른 메시와 반투명 글자의 그리기 순서를 유지한다. 매 프레임 갱신되는 삼각형 참조와 인스턴스 배열은 존재하지만 정점 메시 재생성과는 다르다.

## 2. 버퍼 이용

이전 로그의 드로우콜은 보통 총 15회: 월드 1, UI 1, 후처리 13이었다. 프레임당 평균 약 44,415개 삼각형과 약 470KB의 인스턴스/삼각형 참조 데이터가 전송됐다. 정적 지오메트리는 캐시 미스 또는 아틀라스 재배치 시 업로드한다. 기존 배치 제출 CPU 평균은 0.045ms로, 로그에서 가장 큰 병목은 아니었다.

기존 스트리밍 버퍼는 Flush 때마다 실제 데이터 길이로 `glBufferData`를 호출했다. 이를 고정 용량 저장소 orphaning(`glBufferData(..., nullptr, GL_STREAM_DRAW)`) 후 사용한 범위만 `glBufferSubData`로 올리도록 변경했다. 삼각형 버퍼는 필요할 때만 용량을 두 배로 늘리고 이후 유지한다. 인스턴스 텍스처와 버퍼의 연결은 초기화 시 한 번 지정한다.

GPU가 사용 중인 저장소의 재사용 대기를 줄일 수 있는 구조지만, 드라이버의 무대기 실행이나 FPS 상승을 보장하지는 않는다. 매 Flush의 새 GL 버퍼 객체 생성은 없다. 정적 아틀라스와 반투명 순서도 유지한다. `buffer_orphans`, `stream_capacity_bytes`, 기존 업로드 바이트와 제출 시간으로 비용을 확인한다.

## 3. 그 외 개선

- 프레임 예약: 기존 Update 완료 뒤에 다시 16ms를 기다리던 상대 예약을 60Hz 절대 시각 기준 예약으로 바꿨다. Update 비용이 다음 대기 시간에 계속 더해지는 것을 피한다. 놓친 예약은 건너뛰며 무제한 따라잡기나 busy-wait는 하지 않는다. OS 타이머 지연과 VSync의 영향은 남을 수 있다. 목표는 여전히 60Hz다.
- 청크 스트리밍: 플레이어 청크와 스트리밍 반경이 같으면 마을/지형 청크 목록을 다시 검색하지 않는다. 이동·줌·창 크기 때문에 실제 반경이 달라지면 갱신한다.
- SceneGraph: TickGroup마다 Actor ID 벡터를 복사하지 않고 초기 길이만 고정해 순회한다. 콜백에서 추가한 Actor는 다음 순회에 참여하고, 파괴는 기존처럼 순회 이후 수거한다. 그리기 목록에서는 화면 밖 여부를 먼저 검사해 불필요한 부모 가시성 탐색을 줄인다.
- NPC 경로: BFS 큐를 고정 크기 배열로 바꿔 검색마다 큐의 동적 할당을 줄였다. 막힌 격자 셀을 다른 방향에서 반복 검사하지 않도록 표시한다. 이동 규칙·시야·직업 행동과 원거리 마을 시뮬레이션은 유지한다.
- 후처리: 프로그램의 uniform 위치와 텍스처 단위 지정은 초기화 때 캐시한다. HDR·Bloom·비넷·가장자리 흐림과 블러 횟수/해상도는 그대로 유지한다. GPU 시간 없이 품질을 낮춰 해결했다고 판단하지 않는다.

## 추가 프로파일링

성능 CSV와 session.log는 schema=3이다. 기존 열 뒤에 아래 열을 추가했다.

| 열 | 해석 |
| --- | --- |
| gameplay_cpu_ms | 초기화·플레이어·기존 게임플레이 갱신 시간 |
| npc_cpu_ms | NPC 시뮬레이션과 NPC 내보내기 전체 시간 |
| npc_export_cpu_ms | npc_cpu_ms 안에 포함된 로그/JSON 내보내기 구간 |
| stream_cpu_ms | 카메라·청크 스트리밍·Actor 수거 시간 |
| path_calls / path_nodes | 해당 프레임의 Update에서 호출한 경로 탐색과 BFS 방문 셀 수 |
| unaccounted_ms | 프레임 간격에서 Update·Render·Swap을 뺀 값, 최소 0. 예약 대기·이벤트 루프·이전 로그 출력·OS 스케줄링 등이 포함됨 |
| gpu_world_ms / gpu_post_ms / gpu_ui_ms | 준비된 이전 프레임의 GPU 타임스탬프 구간. 현재 행의 CPU 측정과 같은 프레임이 아님 |
| gpu_sample_age | 해당 GPU 표본이 몇 렌더 프레임 전인지 |
| buffer_orphans / stream_capacity_bytes | 스트리밍 저장소 교체 횟수와 두 버퍼의 용량 합계 |

GPU 측정은 4개 슬롯을 순환하고 완료된 결과만 읽는다. 쿼리가 아직 준비되지 않으면 기다리지 않고 측정을 건너뛴다. 64비트 타임스탬프를 지원하지 않거나 준비된 표본이 없으면 GPU 시간은 -1이다. `glFinish`는 사용하지 않는다. GPU 타임스탬프 구간에는 제출 지연으로 GPU가 쉬는 시간도 포함될 수 있으므로 순수 연산량이나 GPU 사용률과 동일시하지 않는다.

콘솔 1초 요약에 NPC·내보내기·스트리밍·메시 파일 I/O·대기/기타·GPU 단계별 평균을 표시한다. VSync 설정은 가능하면 시작 로그에 SwapInterval로 기록한다. 지원되지 않으면 unavailable로 기록하며 설정을 임의로 바꾸지 않는다.

## 검증 범위와 다음 실행 비교

기존 CSV 분석, 소스 정렬과 정적 검사를 수행했다. 변경 후 빌드·게임·GPU 실행은 수행하지 않았으므로 안정적인 60FPS 달성 여부는 아직 확인하지 않았다. 기존 캐시 파일은 삭제하지 않았다. 캐시가 비어 있거나 처음 보는 글자/소품이 나타날 때의 동기 파일 I/O는 남아 있다. 크기가 제한된 지형 캐시로 이동 중 무제한 파일 생성을 제거했으며, 남은 I/O 스파이크가 관측되면 비동기 파일 처리와 글꼴 텍스처 아틀라스를 후속 개선 대상으로 삼을 수 있다.

같은 Release 구성·해상도·줌·이동 경로에서 새 Profiling 폴더를 이전 기록과 비교한다. 첫 방문과 재방문 구간을 구분하고 p95/p99 프레임 시간, 메시 생성/로드, cacheIO, NPC 경로 탐색량, GPU post/ui 구간을 함께 본다. GPU가 짧고 pacing/other만 길면 게임 처리량 부족과 타이머 제한을 구분해야 한다. 이 문서의 기존 수치를 변경 후 결과로 사용하지 않는다.
