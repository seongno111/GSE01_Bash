# 120 FPS 대응과 CPU 지연 분산

2026-11-05

기본 렌더링 목표를 120 FPS로 변경했다. F8로 60/120 FPS를 전환하며, 전환 시 콘솔과 session.log에 목표값과 프레임 번호를 기록한다. CSV의 target_fps 열로 각 프레임을 구분한다. 120 FPS의 프레임 시간 예산은 약 8.33ms다.

프레임 대기는 Windows 고해상도 waitable timer와 입력 이벤트를 함께 사용한다. 지원되지 않거나 대기가 실패하면 GLFW 이벤트 대기로 전환한다. 입력 이벤트로 일찍 깨어나면 남은 시간을 다시 기다린다. NPC 의사결정과 거점 시뮬레이션은 기존 20Hz 누적 시간으로 진행한다.

## 변경 근거

기존 Release 캡처 20261103-170255-212-3236의 초기 5초를 제외한 2,772프레임에서 업데이트 p95는 약 21.8ms, 렌더 CPU p95는 약 2.9ms였다. 업데이트 82.6ms 프레임에서는 경로 탐색 6,404노드와 모니터링 내보내기 33.3ms가 함께 발생했다. 업데이트 64.3ms 프레임에서는 내보내기 없이 경로 탐색 7,928노드가 발생했다. 이 수치는 변경 전 기록이며 새 코드의 실측 결과가 필요하다.

## 경로 탐색

액터 ID를 키로 사용하는 최대 512개 요청 큐를 두고 하나의 A* 탐색을 여러 프레임에 나눠 이어간다. 프레임당 1.5ms의 시간 목표와 최대 192회 작업 제한을 사용한다. 충돌 검사 한 단계와 결과 정리 비용 때문에 시간 목표를 약간 넘길 수 있다.

직선 이동 검사도 여러 프레임에 분산한다. 이미 유효한 경로는 새 탐색을 기다리는 동안 유지한다. 행동 변경, 사망, 복귀, 이사 등으로 목적이 바뀌면 요청을 취소한다. NPC는 선택한 행동의 접근 단계에서 경로를 검증하고, 도달할 수 없으면 기존 실패 처리와 다음 행동 선택으로 이어진다. 탐색 요청이 몰리면 이동 경로 확보가 늦어질 수 있으며 대기 수를 함께 확인해야 한다.

## 모니터링 내보내기

게임 스레드는 값 스냅샷만 복사한다. JSON 생성, monitor.json 및 latest.log 쓰기는 한 개의 비동기 작업에서 처리한다. 작업 중에는 추가 스냅샷을 쌓지 않고 다음 주기에 최신 상태를 복사한다. 작업자는 Actor, 씬 그래프, 실행 중인 월드 상태에 접근하지 않는다.

임시 파일을 완성한 다음 교체하는 방식과 기존 모니터 JSON 필드를 유지한다. 종료 시 진행 중인 작업을 기다린다. 게임 스레드에는 스냅샷 복사와 작업 시작 비용이 남는다.

## 로그와 확인 순서

Profiling CSV 스키마는 5이며 기존 열 뒤에 다음 열을 추가한다.

- target_fps는 요청된 프레임 제한이다.
- path_cpu_ms는 이번 프레임의 탐색 처리 시간이다. npc_cpu_ms에 포함된다.
- path_pending은 대기 중이거나 진행 중인 요청 수다.
- path_deferred는 이번 프레임에 아직 결과를 받지 못한 요청 호출 수다.
- path_completed는 이번 프레임에 완료한 탐색 수다.
- monitor_capture_cpu_ms는 메인 스레드의 복사와 작업 시작 비용이다.
- monitor_worker_ms는 마지막 완료 작업의 시간이며 프레임 CPU 시간에 더하지 않는다.
- monitor_age_ms는 마지막 성공한 스냅샷을 캡처한 후 경과한 시간이며 성공 전에는 -1이다.
- monitor_skipped는 작업 중이라 캡처를 건너뛴 누적 횟수다.
- monitor_pending은 현재 내보내기 작업의 존재 여부다.

동일한 Release 구성, 해상도, 후처리 설정으로 마을과 적 거점을 이동한다. 초기 로딩, 최소화, F8 전환 직후 집계 구간을 제외하고 FPS와 프레임 시간 p95/p99를 비교한다. path_pending이 지속해서 증가하는지, monitor_age_ms가 갱신되는지도 함께 확인한다.

이번 작업은 빌드와 게임 실행을 수행하지 않았다. 실제 120 FPS 유지 여부는 실행 후 새 로그로 판단해야 한다.
