렌더링 배칭·메시 캐시·프로파일링 개선 리포트
작성: 2026-09-22
상태: 코드 구현 및 소스 검토 완료. 사용자 요청에 따라 빌드/게임 실행/실측은 하지 않음.

1. 사용자 제공 기준 데이터

  6개 콘솔 샘플의 FPS: 37.9, 44.1, 47.6, 47.2, 48.2, 46.5
  각 샘플에서 DrawCalls/frame의 last/avg/min/max는 모두 621.
  샘플 FPS의 단순 산술 평균은 45.25. 전체 세션의 가중 평균 FPS는 알 수 없다.
  기존 로그에는 GPU 시간, CPU 단계 시간, 메시 생성 수, 업로드량이 없다.
  따라서 621회 제출이 비용을 만든다는 구조적 문제는 확인할 수 있지만,
  현재 FPS의 주된 병목이 드로우콜이라는 결론이나 개선 배율은 실측 전 확정할 수 없다.

2. 소스에서 확인한 문제

  기존 Renderer::Flush는 캐시된 메시마다 VAO를 바인딩하고 위치/색상 uniform을
  갱신한 뒤 glDrawArrays를 호출했다. 메시 캐시는 생성 비용만 줄였고 제출 횟수는 줄이지 않았다.
  글리프도 한 글자마다 별도의 메시/드로우콜이었다.
  동적 도형은 연속 구간만 합쳐졌고 중간에 캐시 메시가 들어오면 배치가 나뉘었다.
  지형 타일, 타원, 안개, 각종 효과는 매 프레임 정점을 만들고 동적 VBO로 전송했다.
  반투명 오브젝트가 많으므로 메시 종류로 무작정 정렬하면 기존 겹침과 합성 순서가 바뀐다.

3. 이번에 적용한 드로우콜 감소 방법

  Actor/SceneGraph의 제출 순서를 유지하는 공통 배치 경로를 Renderer에 추가했다.
  Begin -> 도형/DrawCachedMesh 호출을 누적 -> BeginUI에서 월드 배치 제출 및 후처리
        -> UI 누적 -> Flush에서 UI 배치 제출.

  서로 다른 메시의 정점을 하나의 GPU geometry atlas에 저장한다.
  atlas는 RGBA32F 2D 텍스처이며, 정점 하나는 위치/색상/발광 등 8개 float,
  즉 texel 2개로 저장된다. 보통 2048 x 2048, 64 MiB를 할당한다.
  정점 셰이더가 texelFetch로 필요한 정점을 직접 읽는다.

  논리적인 메시 인스턴스는 두 축, 위치, 색상, 발광 배율을 담은 48바이트 데이터다.
  삼각형마다 atlas 정점 시작 위치와 논리 인스턴스 번호를 8바이트로 기록한다.
  한 번의 glDrawArraysInstanced(GL_TRIANGLES, 0, 3, triangleCount)로 배치를 그린다.
  OpenGL 인스턴스 하나가 삼각형 하나인 구현이다. 논리 오브젝트 수와 GL 인스턴스 수는 다르다.
  이 방식은 같은 메시만 묶는 일반적인 메시 단위 인스턴싱과 달리,
  다른 형상의 메시와 글리프도 하나의 배치에 원래 순서대로 포함할 수 있다.
  glMultiDraw로 호출 수만 한 번처럼 세는 방식은 사용하지 않았다.

  각 배치의 한도는 논리 인스턴스 16,384개 이하(드라이버 한도도 반영),
  삼각형 262,144개다. 한도에 도달하면 기존 순서대로 먼저 제출하고 계속 누적한다.
  atlas 재배치 전에도 누적된 배치를 먼저 제출해서 이전 정점 주소를 보호한다.
  드로우콜 카운터는 실제 glDrawArraysInstanced/glDrawArrays 호출 직후에 증가한다.

4. 매 프레임 메시 생성 제거와 파일 재사용

  정적 복합 메시: 지형/블록/나무/성당/캐릭터/적/글리프를 메모리와 파일에 캐싱한다.
  지형 키에는 variant, 길 여부, 지역 색상, 오염 표현 단계, 격자 표시 여부를 반영한다.
  카메라 위치와 줌은 키에 넣지 않는다. 타일 가장자리 보정 폭도 줌과 함께 확대되도록 통일했다.

  동적 표현: 삼각형/사각형/선/타원/안개의 기본 메시를 한 번 만든 뒤 재사용한다.
  불꽃의 움직임, 체력 바의 길이, 그림자 크기, 투명도는 변환과 tint로 바뀐다.
  애니메이션 매 순간의 형상을 별도 파일로 저장하지 않아 파일 수가 폭증하지 않는다.
  CPU에서 매 프레임 인스턴스 데이터와 삼각형 참조 목록은 여전히 작성한다.
  이것은 메시 정점 생성과 구분하며 업로드량을 별도 측정한다.

  캐시 조회: 메모리 -> 실행 파일 옆 MeshCache/v1/*.mesh -> 생성 콜백 -> 파일 저장.
  최초 실행이나 새로운 변형 등장 시 생성/파일 기록이 발생하는 것은 정상이다.
  다음 실행은 파일을 읽어 GPU atlas에 다시 업로드하지만 메시 생성 콜백은 생략한다.
  이미 메모리에 있는 메시를 계속 그리면 정점 생성과 geometry 업로드는 발생하지 않는다.
  파일에 저장되는 것은 GL 핸들이 아닌 로컬 좌표 정점 데이터다.

  파일 검증: magic, 버전, 전체 키, 정점 개수/삼각형 배수/용량 제한,
  체크섬, 유한 수 여부, 파일 끝을 확인한다. 손상 파일은 거부하고 다시 생성한다.
  저장은 임시 파일을 닫은 후 교체한다. 저장 권한/디스크 문제는 메모리 캐시로 계속 진행한다.
  디스크 예산은 버전 폴더별 256 MiB. 도달하면 추가 저장만 중단하고 기존 파일은 읽는다.
  GPU atlas는 고정 용량이고 CPU 정점 사본도 보관하므로 geometry 저장에
  CPU 최대 약 64 MiB + GPU 64 MiB가 들 수 있다. 폰트 정보/인스턴스 버퍼 등은 별도다.
  메모리 캐시는 프레임 경계에서 4,096개를 넘으면 오래된 항목부터 줄인다.
  atlas 공간 부족 시에도 퇴출/재배치하며 재업로드량을 로그에 기록한다.
  메시 형상/폰트/직렬화 형식 변경 시 RendererMeshCache.cpp의 CacheVersion을 올리거나
  InvalidateMesh(key)를 사용해야 한다. 빌더의 소스 변경을 자동 감지하지는 않는다.

5. 예상 제출 수: 실측 결과가 아닌 코드상 계산

  용량 초과나 atlas 재배치가 없고 월드와 UI에 각각 그릴 내용이 있을 때:

  후처리 설정                         월드 + UI + 후처리 = 합계
  Bloom + Edge blur                  1 + 1 + 13 = 15
  Bloom만                            1 + 1 +  8 = 10
  Edge blur만                        1 + 1 +  6 = 8
  후처리 켬, Bloom/Edge blur 끔       1 + 1 +  1 = 3
  후처리 전체 끔/사용 불가            1 + 1 +  0 = 2

  Bloom은 추출 1회 + 블러 6회, 가장자리 블러는 축소 1회 + 블러 4회,
  최종 합성은 1회다. 비네트는 최종 합성에 포함되어 별도 호출을 추가하지 않는다.
  기본 설정에서 621 -> 15는 조건부 예상치이며, 실제 수정 후 로그로 확인해야 한다.
  GPU 픽셀 처리량, 삼각형 수, 후처리 패스 수는 배칭만으로 줄어들지 않는다.

6. 분석용 로그

  실행 파일 옆 Profiling/<날짜-시각-밀리초-PID>/에 실행별로 저장한다.
  session.log: 빌드 시각, Debug/Release, GPU/드라이버/GLSL, 초기 해상도,
               1초 단위 FPS/드로우콜/CPU 평균/프레임 시간 p50/p95/p99/최대.
  frames-N.csv: 완료한 모든 프레임의 원자료. 1초 정도 메모리에 모아 파일에 쓴다.
                64 MiB마다 새 part로 나누며 정상 종료 시 남은 자료도 저장한다.
  강제 종료 시 아직 기록하지 않은 약 1초의 마지막 자료는 유실될 수 있다.
  로그 폴더는 누적 보관하며 자동 삭제하지 않는다. 필요에 따라 보관/정리한다.

  분석 축:
  - 전체/월드/UI/후처리 드로우콜, 배치 수, 논리 인스턴스와 삼각형 수
  - 메모리 캐시 수/바이트, hit/miss, 실제 생성/디스크 로드/저장/거부/저장 생략
  - geometry와 instance 업로드 바이트, 배치 용량 초과, atlas 재배치, 캐시 퇴출
  - CPU update/render/swap, 파일 읽기/쓰기, 빌더, atlas 업로드, 배치 제출 시간
  - 해상도, 후처리 사용 가능 여부와 모든 효과 설정
  - 직전 요약/로그 flush 비용

  자세한 필드 정의는 성능_로그_안내.txt를 참고한다.
  render_cpu_ms는 CPU 제출 시간이고 GPU 시간은 아니다. OpenGL 드라이버 대기도 포함될 수 있다.
  세부 CPU 시간은 render_cpu_ms에 포함되므로 모두 더해서 전체 시간으로 해석하면 안 된다.
  swap_ms가 길어도 GPU 계산, VSync, 운영체제 스케줄링 중 어느 하나로 단정할 수 없다.
  현재 16ms GLUT 타이머와 콘솔/파일 출력 비용도 FPS에 반영된다.
  GPU timestamp/query, GPU 메모리 사용량, VSync 상태, OS CPU 사용률은 이번 범위에 없다.

7. 사용자 실행 시 비교 절차

  1) 동일 해상도/줌/장소/효과/빌드 설정을 사용한다. Debug와 Release는 별도 비교한다.
  2) 첫 실행을 기록해 생성/저장 시점의 프레임 시간과 p99를 본다.
  3) 정상 종료 후 다시 실행해 disk_loads 증가, mesh_builds 감소 여부를 본다.
  4) 제자리에서 안정화한 구간의 mesh_builds/geometry_upload_bytes가 0에 가까운지 본다.
     UI의 처음 등장하는 글자나 새 상태에서는 일부 생성/업로드가 정상이다.
  5) 이동, 줌, 격자 전환, 전투, 변이/죽음, 보스, 후처리 토글 구간을 각각 기록한다.
  6) draw_calls가 world_draws + ui_draws + post_draws와 같은지 본다.
     batches는 world_draws + ui_draws와 같아야 한다.
  7) 긴 프레임에 disk I/O, atlas_repacks, capacity_flushes, 큰 인스턴스/삼각형 수가
     같이 나타나는지 확인한다. 동일 조건의 정상 프레임과 비교한다.
  8) 겹치는 나무/캐릭터/반투명 안개/한글 글리프 순서와 HDR 발광을 화면에서 확인한다.

8. 이후 개선 우선순위와 판단 기준

  A. 폰트 텍스처 atlas
     글자 윤곽을 현재 여러 사각형으로 만든다. 글자당 텍스처 사각형 하나로 바꾸면
     삼각형 참조 수, 셰이더 실행 수, 업로드량을 함께 줄일 수 있다.
     UI가 켜질 때 triangles/instance_upload_bytes가 크게 증가하면 우선 검토한다.

  B. 로딩 단계 사전 생성/비동기 파일 I/O
     첫 방문 시 디스크 읽기/쓰기와 빌더 호출은 현재 렌더 스레드에서 동기 실행한다.
     cold 구간의 p99와 disk_read_ms/disk_write_ms가 함께 증가하면 검토한다.
     GL 업로드는 컨텍스트 소유 스레드에서 처리하고 작업 스레드는 파일/CPU 생성만 담당한다.

  C. 프러스텀/화면 컬링 강화와 청크 단위 정적 묶음
     기존 Actor InView가 사용된다. 불필요한 여백과 장면 순회/정렬을 분석한 다음
     화면 밖 액터 제출과 고정 지형 처리 비용을 줄인다. 반투명 순서는 유지해야 한다.

  D. 인스턴스 참조 재사용, 버퍼 스트리밍 개선
     현재 매 배치 glBufferData로 인스턴스와 참조 목록을 전송한다.
     정적인 참조 목록 캐싱, 링 버퍼, 지원 환경의 persistent mapping을 검토할 수 있다.
     단, GPU 사용 중인 영역을 덮어쓰지 않도록 fence/수명 관리가 필요하다.

  E. 후처리 비용과 GPU 시간 측정
     draw_calls는 낮은데 render/swap 시간이 높다면 GPU timer query를 지연 조회하여
     월드/후처리/UI 비용을 구분한다. 블룸/블러 해상도와 반복 수 변경은 화질 비교를 동반한다.
     드로우콜 감소를 위해 의존 관계가 있는 블러 패스를 무조건 합치지 않는다.

  F. 일반 메시 인스턴싱/간접 제출과 현재 방식 비교
     이번 삼각형 단위 인스턴싱은 순서 보존과 다양한 메시 배칭을 우선한 구조다.
     정점 텍스처 조회와 삼각형별 참조 비용이 추가된다. 모든 GPU에서 더 빠르다고 보장하지 않는다.
     불투명한 같은 메시가 많이 모이는 경우에는 일반 메시 단위 인스턴싱이 유리할 수 있다.
     더 높은 GL 버전을 전제로 하는 간접 제출/SSBO 방식은 호환성 범위를 먼저 결정해야 한다.

9. 변경 위치

  Renderer.h/.cpp: 공통 배치, 기본 도형 인스턴싱, 통계, 실제 glDraw 카운터.
  RendererMeshCache.cpp: 파일 캐시, 검증, 정점 atlas 업로드/재배치/퇴출.
  Shaders/SolidRect.vs: atlas 정점 조회 및 인스턴스 변환/색상/HDR 처리.
  ActorVisuals.cpp: 지형 복합 메시 캐시.
  FrameProfiler.h/.cpp: CSV/세션 로그, CPU 단계 시간, 구간 통계.
  SimpleGame.cpp: 갱신/렌더 제출/버퍼 교환 측정 경계 연결.
  vcxproj/filters: 새 소스 등록. .gitignore: 생성 캐시/프로파일 폴더 제외.

10. 기술 근거

  Khronos Primitive Order: 인스턴스 순서는 작은 gl_InstanceID부터이며,
  블렌딩처럼 순서가 필요한 연산은 primitive order를 따른다.
  https://wikis.khronos.org/opengl/Primitive_Order

  구현/검토 기록일은 2026-09-22이며, 위 예측은 실측 보고가 아니다.
  후속 측정은 해당 실행의 Profiling 폴더와 비교 조건을 함께 보관한다.

추가 분석 맥락 및 정적 검토 기록
  CSV는 현재 63개 필드다. 카메라/플레이어 좌표, 줌/격자 상태,
  그래프 액터 수/로드 청크 수/월드 및 UI 표시 목록 수와 목록 작성 CPU 시간도 기록한다.
  SceneGraph의 계측은 목록 조회·컬링·정렬에만 시간을 더하며 처리 순서는 유지한다.
  소스 검토에서 프로젝트/필터의 새 소스 등록, CSV 헤더와 출력 필드 수 일치,
  수정한 주요 클래스의 중복 메서드 정의 여부와 diff 공백 검사를 확인했다.
  이는 컴파일/링크, 셰이더 컴파일, GPU 렌더링 검증을 대체하지 않는다.
